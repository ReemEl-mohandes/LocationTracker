# F7 — Upload Queue Durability & Batching (characterization)

`UploadQueue.enqueue` / `flush` / `dropSent` / `persist`. Services: **S3 LocationAPI**,
**S5 PointStore**, **S4 TokenStoring**, **S9 BackgroundTaskRunning**, **S10 Clock**.

## Model / rules (queue state)

### F7.1 Enqueue persists — happy
- **When** `enqueue(p)`
- **Then** `p` appended; `PointStore.save([...,p])` called; `pendingCount` incremented.

### F7.2 Cap enforced — edge
- **Given** `maxQueuedPoints (20000)` already queued
- **When** `enqueue(p)`
- **Then** the oldest is dropped so length stays 20000 (FIFO trim).

## Controller (flush)

### F7.3 Happy batch — happy
- **Given** 700 points queued, token present, online
- **When** `flush()`
- **Then** `LocationAPI.uploadBatch` called first with the oldest **500** (maxBatchSize), on 2xx
  those 500 dropped and persisted, then a second call with the remaining 200; queue empties;
  `lastUploadAt`/`lastUploadSummary` set; the whole run is wrapped by
  `BackgroundTaskRunning.run("upload-locations", …)`.

### F7.4 Guards — edge
- No token → returns immediately, no API call.
- Empty queue → returns.
- Already flushing → returns (reentrancy guard).
- `notBefore` in the future → returns.

### F7.5 Rate limited (429) — error
- **Given** `uploadBatch` throws `rateLimited(retryAfter: 30)`
- **Then** `notBefore = now + 30 s` (or +30 default); batch **not** dropped; loop stops;
  `lastError` set to the busy message.

### F7.6 Permanent 4xx — error (deliberate drop)
- **Given** `uploadBatch` throws `server(status:400,…)`
- **Then** the batch **is dropped** (it will never be accepted), `lastError` records it, and the
  loop continues to the next batch. // TODO: bug? — a 400 caused by a transient server bug would
  silently discard points. Record as-is; confirm before Phase 4.

### F7.7 Offline / 5xx — error (retryable)
- **Given** `uploadBatch` throws a network error or `server(status:503,…)`
- **Then** points are **kept**, loop stops, `lastError` set; a later flush retries.

### F7.8 Prefix stability — edge
- Points may be appended (by `enqueue`) while a batch is in flight; the sent prefix is still the
  prefix on response, so `dropSent(count)` removes exactly the sent points, never newer ones.

## Service seam note
`persist()` writes with complete-until-first-unlock file protection and is a **no-op while
`diskLoaded == false`** (see F10).
